# 正式包启动资源优化（2026-09-21）

## 结论

在保留全部 38 条工作区绑定、启动阶段继续预热 Quick-Ask 的情况下，两轮 macOS 正式包对比中，Electron 主进程峰值物理内存从约 2,660 MiB 降至 89 MiB（约 -97%），启动后 65 秒内累计 CPU 时间从约 112 秒降至 1.2–1.8 秒（约 -99%）。

整个进程树的同期峰值内存从 4,270–4,690 MiB 降至 1,867–2,205 MiB；累计 CPU 时间从 141 秒左右降至 24–33 秒。两轮平均分别减少约 55% 和 80%。剩余最大开销是 DSH 运行时；未修改任何 `@deepseek-ai/*` 依赖源码、锁定版本或补丁。第二阶段的锁文件仅新增一个 Amiba 内部 workspace 引用。

## 做了什么

1. **绑定工作区只保存元数据，不再为每个历史会话递归监听整个项目。** 原本 38 个会话恢复时会建立 38 个目录监听，其中 29 个指向同一个大目录，重复遍历、路径对象和事件处理堆积在 Electron 主进程。工作目录、会话绑定及持久化语义保留。
2. **旧文件预览和本地资源观察 API 都按打开的文件订阅。** 相同规范化根和文件共享一个原生监听；每次订阅先做路径授权。最后一个订阅关闭即释放，窗口导航、销毁、工作区重绑定和初始化中取消都能清理，仍能感知文件删除、重新创建及文件被目录替换。第一阶段未接入新 DSH 资源提供器；第二阶段补上了下述按需适配。
3. **空闲启动时，桌宠活动摘要不再冷读上一段完整会话日志。** 使用索引里的标题和 idle 状态；运行中的会话继续跟踪日志，启动后新发生的短任务即使在两次轮询之间结束，也会获取终态。已订阅任务保留到终态事件，拒绝旧会话迟到事件。本项只改变展示摘要，不改变执行、审批或历史恢复。
4. **自有 UI shell 内嵌的 PDF 二进制资源逐项无损压缩。** 字体、CMap、WASM 仍全部随包提供，只在 PDF.js 请求对应资源时解压；不留下永久解压缓存。189 项资源逐字节一致，许可证保留。资源 base64 合计从 4,611,428 降至 2,748,312 字节；自有 shell 的实际 `client.js` 从 13,037,415 降至 11,174,456 字节（-14.3%）。这不意味着 DSH 整体内存同比下降。

Quick-Ask 窗口创建和预热时机未改。随任务另行修正了基线已有的两个 worker 类型导入及桌面 TypeScript 检查配置，使完整类型检查可运行。

## 测量方式

- 基线：`origin/main` 的 `d9b67021`；第一阶段优化版：`5c8d4c0c`。两者均为完整 production build 后按发布排除规则暂存 runtime、通过 electron-builder 生成的 macOS arm64 `.app`，Electron 33.4.11，应用版本 0.1.9。
- 本地 ad-hoc 签名并通过 `codesign --verify --deep --strict`。未发布安装包、未进行开发者签名/公证，未覆盖 `/Applications/Amiba.app`。
- Apple M4 Pro、14 逻辑核、48 GiB 内存、macOS 26.6.2。
- 每轮使用同一份实际用户数据快照的独立 APFS 克隆，保留 38 条绑定、4 个实际目录以及原有插件配置；直接启动包内可执行文件。未删除绑定来制造改善。
- 顺序为基线 1、优化 1、基线 2、优化 2；每轮 65 秒，无用户交互，不并行构建/测试或运行另一份 Amiba。没有开发服务器、Node inspector 或 renderer CDP；功能 QA 的调试连接与解除后台绘制限速参数不用于性能测量。
- 每约 250 ms 通过 macOS `proc_pid_rusage` 采集进程树，CPU user+system 计数按 Mach timebase 转换为秒；100% CPU 表示一个逻辑核。主进程峰值用内核 lifetime physical-footprint 最大值；进程树峰值是同一采样时刻的各存活进程 physical footprint 之和，**不是各进程独立峰值相加**。
- 各轮均在启动阶段对 main/DSH 运行相同的 `sample`，末段采集 `vmmap`。数据为本机两个独立进程启动样本，不是跨平台结论，也不是清空操作系统磁盘缓存的冷机测试。

### 明确的验证限制

- PDF 全目录单测中另有两个套件因已发布 DSH 包缺少 `anser` / `zustand` 的可解析开发依赖而无法收集。本次未篡改依赖来绕过，不能声称整个 PDF 测试目录全部通过。
- 原开发插件冒烟入口在正式包中被禁用，正式包功能 QA 因此改用应用实际接口和页面。
- 第一阶段完整 PDF 冒烟在外部写入通知处失败：官方提供器只转发 `fs/observed`。第二阶段通过 Amiba 适配补齐该能力，原始 `.cache` 路径完整冒烟已通过，见下文。
- 未测试 Windows/Linux 的正式包，未测长时间工作负载或真实模型首 token 延迟。

## 第二阶段：事件索引、外部编辑和插件边界

### 实现与语义

- **会话索引改为增量事件更新。** 复用主进程原有 `$events` + `session/control` 通道，处理新增、运行状态、活动、标题和 `sessionListMetadata`；桌宠活动使用同一个事件分发，不新增审批消费者。完整列表从每 2 秒一次改为连接建立/重连时读取，以及每 30 秒兜底对账；未知会话或卸载事件合并触发补读，读取失败每 2 秒重试。
- 首次完整快照之前缓存增量，避免把陆续恢复的历史会话误判为启动后新活动；请求期间的新事件会覆盖返回的旧快照。`removed` 只表示离开 live registry，不能直接删除持久化历史。后台主进程生命周期、审批/问题等待、任务终态、子会话父关系与 journal 断线补帧均保留。删除/预设等宿主事件覆盖不完整的变化仍依靠最多 30 秒兜底对账。
- **官方文件提供器加按需本地适配。** 仅在资源有订阅或 pin 时观察一个文件，使用官方 stat 返回的绝对路径；本地事件合并为 50 ms 一次失效，重开官方流取权威元数据，读取内容、版本和错误仍由 DSH 决定。观察器 ready 后补读一次，关闭最后一个持有者即释放；没有闲置轮询，也没有恢复整目录递归监听。原来未使用的本地 1 秒 stat 兼容提供器被此适配替代。
- 原生观察权限较官方读取范围窄时（例如文件不在绑定工作区），保留官方预览与官方事件，不扩大本地权限；这种文件的进程外编辑仍不能保证自动通知。
- **只修正两处明确遗漏的共享引用。** 浏览器插件的 `@amiba/ui/plugin` 映射到已有 shell 公共出口，记忆插件的 `streamdown` 同样使用已有出口。没有删除 UI/Streamdown 公共导出，没有改 DSH loader、依赖源码或第三方构建产物。

### 包体证据

以实际 production `client.js` 和 source map 映射归属分析，浏览器插件原先因漏配 external 带入 CodeMirror、Streamdown、parse5 等；记忆插件通过 `@amiba/markdown` 又带入 Streamdown 及解析依赖。修正引用后：

| 客户端 | 第一阶段（字节） | 第二阶段（字节） |
| --- | ---: | ---: |
| browser-core | 911,006 | 7,750 |
| memory-memos | 629,563 | 136,902 |
| ui-shell | 11,174,456 | 11,176,006 |

两个消费插件合计减少 1,395,917 字节；公共 shell 仅因预览适配增加约 1.5 KB。Source map 归属用于定位，不当作内存测量。Shell 单独的 PDF worker、语法高亮语言和公开 UI 出口不是本次可随意删掉的重复模块；各插件 Zod schema 的重复仍保留，改成 mini 或统一共享需要单独验证完整校验行为。

### 最终正式包复测

仍使用上述设备、65 秒采样方式、38 条绑定和同一份新的用户数据快照。基线为第一阶段 `5c8d4c0c` 的正式包；最终版为第二阶段全部实现及首次快照边界修复后的正式包。均本地 ad-hoc 签名验证通过，无 CDP/inspector、无开发服务器，采样期间不构建或修改仓库。

先完成两组基线/候选包对照；补上首次快照回归保护并重新打包后，再测最终包两次。下表只使用两次基线与两次最终包结果，未把中间候选包当作最终版本。

| 指标 | 基线 1 | 基线 2 | 最终 1 | 最终 2 |
| --- | ---: | ---: | ---: | ---: |
| 主进程峰值（MiB） | 89 | 89 | 86 | 86 |
| 主进程累计 CPU（秒） | 1.24 | 1.10 | 0.88 | 0.83 |
| DSH 峰值（MiB） | 1,138 | 1,177 | 1,064 | 1,066 |
| DSH 累计 CPU（秒） | 19.24 | 20.72 | 18.46 | 17.03 |
| 进程树同时峰值（MiB） | 2,150 | 2,237 | 2,251 | 2,258 |

DSH 峰值两轮平均约减少 **8%（约 93 MiB）**，其累计 CPU 约减少 11%；主进程累计 CPU 少约 0.32 秒。所有数字只代表本机两次启动样本，不是跨平台或长期负载承诺，也无法把组合改动的全部收益单独归因于某一个包。

**本轮没有测得整个进程树的峰值内存或累计 CPU 改善。** 主 renderer/GPU 的绘制、窗口遮挡节流和 GC 波动很大：基线 1 renderer 累计 CPU 3.61 秒，基线 2 为 15.24 秒；最终两轮为 13.56 和 15.20 秒。因此不以较小 JS 包或 DSH 的局部改善宣称整体资源同比下降。

## 0.1.10 发版复核

在 `f268a1f9` 的正式包测量后，发版复核补上一个启动竞态：审批/问题事件可能先于首次会话列表返回，导致活动视图尚未选中会话而漏报等待状态。现在保留首次快照之前尚未解决的交互，快照通知后再交付；取消事件会移除缓存，初始连接重建时清理旧缓存并接收宿主重放。新增回归测试覆盖审批、提问和取消。

根包和桌面产品版本统一升至 0.1.10。桌面测试增至 **151/151**，发布工具测试 **29/29**、产品版本/更新入口测试 **7/7**，离线 frozen-lockfile 检查和桌面完整 typecheck 通过。上述性能表对应 `f268a1f9` 的 0.1.9 本地测量包，不冒充 0.1.10 发布安装包的重新测量。

## 仍值得做的优化

1. DSH 模块解析/编译、注册表源码或 source map 缓存、会话 JSONL 恢复仍是大头；建立上游复现，通过正式升级解决。
2. 继续用模块归属与实际 DSH 峰值评估剩余包体，尤其 schema 和高亮资源；保留插件公共 API 和各功能所需资源，不能把“重复出现”直接视为可删除。
3. 对照测量 renderer/GPU 的可见/遮挡状态与动画负载，解释整体开销波动；本轮不更改 Quick-Ask 预热或用户可见动画行为。
