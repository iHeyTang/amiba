# Hermes 0.20 与 Amiba 能力覆盖审计

> 日期：2026-08-07
>
> 目标：确认 Amiba 在 CLI、Desktop 和 Web/浏览器三类入口上，至少覆盖 Hermes 官方 0.20 的产品能力
>
> 结论性质：基于代码的现状审计，不是产品宣传清单

## 1. 结论先行

Amiba 已经覆盖了 Hermes 最核心的 Agent 使用链路：对话、流式推理、Tool 执行、权限审批、附件、模型与 Profile、Skills 查看和启停、Toolset 配置、定时任务、语音输入、工作区文件预览，以及 Desktop 和浏览器两种日常入口。

但如果目标是“第三方 Amiba 的能力至少覆盖官方 Hermes”，目前还不能判定为完成。差距主要不在模型能不能回答，而在以下六类产品能力：

1. **完整的会话生命周期**：现有标题搜索和 Agent 内容搜索已经可用，但分支/派生、回放、Checkpoint 回滚、导入导出和批量维护尚未形成完整 UI；消息正文的全量搜索也还没有直接 UI。
2. **开发工作区**：缺少官方 Desktop 的 Project / 多目录 / Repo / Worktree 模型、持久终端和完整 Git Review。
3. **能力安装与连接**：Skills Hub、MCP 新增/测试/OAuth/目录安装、插件安装更新仍主要依赖 Agent 代操作，缺少确定性的直接管理界面。
4. **远程与运维控制面**：缺少远程 Gateway / Hermes Cloud 连接，以及 Dashboard 中的配置、环境变量、备份、Doctor、安全审计、Hooks、Pairing、Webhook 等管理能力。
5. **运行中的 Agent 可观测性**：缺少官方 Desktop 的子 Agent 树、排队/运行/失败状态、Token 和文件活动观察，以及 Starmap / Curator 学习视图。
6. **长期内容与创作管理**：官方的 Artifacts 浏览和会话内 HTML/SVG/代码预览尚未被 Amiba 当前产品覆盖；这部分应按已经冻结的方案并入统一 Extension Center，而不是再增加一个 Artifact 一级概念。

因此，最准确的判断是：

> Amiba 已覆盖 Hermes 的核心 Agent Runtime 和主要对话体验，但还没有覆盖 Hermes 的完整产品控制面。统一 Extension 方案可以在“内容、交互应用、CLI/后端工具”这一维度做成官方 Artifact 能力的超集；会话、工作区、运维、连接和可观测性仍需要单独补齐。

## 2. 审计口径

### 2.1 基线

Hermes 官方基线固定为：

- 版本：`0.20.0`
- Release tag：`v2026.8.3`
- Commit：`3c27eb6234bf91b8ceee9e9071591b31e9b148cb`
- 发布日期：2026-08-03

Amiba 当前 Runtime Manifest 同样标记为 `0.20.0`，但固定在 `863e31318553cda8ad61df681d08175364d4164b`。该提交比官方 Release tag 晚 292 个提交，因此本报告用官方 tag 判断“官方 0.20 有什么”，用 Amiba 当前工作树判断“我们已经暴露了什么”。

现有 `backend/docs/api-parity.md` 已经落后于代码：它仍把 Profiles、Tools、Logs 等当前已有路由列为缺口，因此没有作为本次结论依据，后续应改为自动生成。

### 2.2 什么叫“覆盖”

能力覆盖不要求逐页复制官方界面，也不要求 `amiba` 和 `hermes` 拥有完全相同的命令名。满足以下任一条件即可视为覆盖：

- 在 Amiba Desktop、浏览器或 CLI 中有稳定、可发现、可操作的入口；
- 由 Amiba 明确提供官方 Hermes CLI 的受支持透传入口；
- 某项管理能力被合并进更统一的 Amiba 产品对象，但用户能够完成同样或更强的任务。

仅仅“代码存在于内置 Hermes Runtime 中”不算产品覆盖。如果普通用户无法找到、调用或恢复失败，它只能标记为“Runtime 可用”。

### 2.3 状态标记

| 标记 | 含义 |
|---|---|
| ✅ 已覆盖 | 已有稳定的 Amiba 产品入口，主要任务可以完成 |
| 🟡 部分覆盖 | 主链路存在，但缺少重要操作、可见性或恢复能力 |
| ↗ Runtime 可用 | 内置 Hermes 已具备，Amiba 没有正式暴露或只可通过隐式命令使用 |
| 🧭 已设计 | 目标方案已明确，当前尚未实现 |
| ❌ 未覆盖 | 当前 Amiba 产品和适配层均未提供等价能力 |

### 2.4 三个官方 Surface 的角色

| 官方 Surface | 主要角色 | 审计原则 |
|---|---|---|
| CLI / TUI | 高级对话、脚本化操作、诊断和全部管理命令 | 不必复制几十个命令，但必须提供透传或等价入口 |
| Desktop | 日常对话、项目工作区、预览、终端、Git Review、Agent 观察 | 属于 Amiba Desktop 的主要对标面 |
| Web Dashboard | 远程 Chat、配置、文件、能力安装和系统运维 | 可以合并进 Desktop，不强制再做一套独立 Dashboard |

## 4. 分模块详细审计

### 4.1 对话、交互与会话生命周期

Hermes 0.20 的 CLI/TUI 和 Desktop 不只是“聊天窗口”。它还包含会话恢复、排队、干预、分支、回放、上下文压缩、后台执行和 Checkpoint 回滚。

Amiba 已经具备：

- `/v1/runs` 流式对话；
- 文本、Reasoning、Tool 参数、Tool 结果和 Inline Diff 展示；
- Tool 审批以及“本次 / 本会话 / 始终 / 拒绝”决策；
- 运行中继续输入并排队；
- 图片、文件和音频附件；
- Session 新建、切换、重命名和删除；
- 会话列表标题搜索；
- 由 Agent 调用 `session_search` 检索历史内容；
- 后台 Session 完成/失败提示；
- Hermes Slash Command 的搜索和发送，因此部分高级能力可以通过命令触发。

这里需要澄清“搜索”的口径：当前侧栏搜索会在已经加载的 Session 中按标题过滤；`session_search` 可以由 Agent 搜索历史内容。官方额外提供的是面向用户的服务端全文搜索页，可以直接搜索全部消息正文、Tool 结果和所有 Profile。它属于现有搜索的增强，不是从零补一套搜索。

仍需补齐：

| 缺口 | 影响 | 建议 |
|---|---|---|
| 全部消息正文的直接搜索 UI | 不经过 Agent 时，只能按已加载会话的标题过滤 | 复用现有入口，按需扩展为服务端 FTS，并支持 Profile、来源、日期筛选 |
| Branch / Fork 与父子关系 | 无法从某个历史节点安全尝试另一方向 | 以 Session lineage 显示“从这里继续” |
| Replay / Replay Diff | 难以复现 Agent 行为或比较重跑结果 | 优先作为开发者模式能力 |
| Checkpoint / Rollback | 文件修改失败后缺少一键恢复 | 与 Workspace 和 Git Review 一起实现 |
| 压缩与上下文状态可见性 | 用户不知道会话是否已压缩、剩余上下文如何 | 显示上下文使用量并提供压缩操作 |
| Session 导入、导出、Prune、批量删除、统计 | 迁移和维护能力不足 | 合并到“会话管理”页，而非分散在设置中 |
| Clarify / Secret / Sudo 专用交互 | 普通 Tool 卡片不足以表达安全输入 | 增加结构化输入事件，Secret 必须遮罩且不写入消息 |

结论：对话主链路已覆盖，但“可恢复、可派生、可迁移”的完整会话产品还未覆盖。

### 4.2 模型、Provider、推理与多模型协作

Amiba 在这一模块已经比较接近官方：

- 主模型、辅助任务模型和各 Profile 独立模型；
- Provider 模型目录和凭据配置；
- MoA / 多模型协作；
- Reasoning 相关配置；
- 能识别环境、外部 CLI、OAuth 和 Hermes Credential Pool 提供的现有凭据。

主要差距不是“能否使用”，而是“能否在 Amiba 中完成连接全生命周期”：

- 缺少统一的 Provider OAuth 登录、刷新、退出和故障修复流程；
- Credential Pool 可以被识别，但缺少直接新增、排序、禁用、删除的管理界面；
- 缺少官方 Dashboard 那种面向高级用户的完整配置 Schema 和 Raw YAML 入口。

建议保留 Amiba 当前的简化模型设置，同时在“高级设置”中补齐 OAuth 和凭据池，不把原始配置暴露给普通用户。

### 4.3 Tools、Terminal Backend、Computer Use 与浏览器

这部分 Amiba 核心能力已覆盖，而且产品表达比官方 Dashboard 更集中：

- 浏览 Toolsets、查看说明、启用/禁用和配置 Provider/模型/环境变量；
- Terminal Backend 可选择本机、Docker、Modal、Daytona、SSH 等 Hermes 支持的执行环境；
- Computer Use 权限开通；
- Web/Browser、图片、视频、Vision、TTS 等能力入口；
- Tool 调用过程和结果展示；
- 浏览器扩展提供真实网页上下文、`@page` 和浏览器执行桥接。

这里需要区分两件事：

- **Agent 拥有 Terminal Tool**：Amiba 已覆盖。
- **用户拥有一个持久交互终端 Pane**：Amiba 尚未覆盖；旧安装引导及其临时 PTY 已移除。

官方 Desktop 的终端 Pane 可以并行保留多个 Shell、与工作区关联并直接观察命令。它属于开发工作区能力，不能用 Tool 日志完全替代。

### 4.4 Skills、Plugins 与 MCP

Amiba 当前覆盖情况：

| 对象 | 已有能力 | 关键缺口 |
|---|---|---|
| Skills | 列表、搜索/筛选、来源和使用信息、文件查看、启用/禁用 | Hub 搜索、预览、安装、卸载、更新、Diff、直接编辑/创建 |
| Hermes Plugins | 列表、启用/禁用、部分来源可卸载 | 安装/更新依赖 Agent 代操作，缺少 Hub 和确定性进度/失败恢复 |
| MCP Servers | 已安装列表、状态展示、Agent 代新增/配置 | 直接 CRUD、连接测试、启用/禁用、OAuth、Catalog 安装 |
| Amiba Extensions | 本地添加、重载、卸载、页面贡献、Main Process 能力 | 个人托管、Revision、统一搜索、权限真正执行尚未完成 |

“让 Agent 帮我安装”是很好的自然语言入口，但不应成为唯一入口。对于安装、OAuth、删除、回滚等确定性操作，仍需要直接 UI 和可审计状态。

另外，现有 Extension Manifest 虽然声明权限，但代码仍明确处于 Phase 1、尚未真正执行权限隔离。统一 Extension 方案上线前，权限必须在 WebView、Host API、MCP Client 和 Runtime 四层生效，否则不能把它视为安全可用的个人后端 Runtime。

### 4.5 Project、Workspace、文件、终端与 Git

Hermes Desktop 0.20 的工作区模型是：Project 可以管理多个目录、Repo、Worktree 和 Session，并把文件树、预览、终端、Diff Review 和提交/交付动作放在一起。

Amiba 当前有：

- 每个 Session 绑定一个本地目录；
- `@file` 搜索与工作区上下文注入；
- 文件树、CodeMirror 预览和文件变化监听；
- Tool 结果中的 Inline Diff 和代码执行结果；
- Workspace Pane 多标签和固定预览。

尚缺：

- 独立 Project 实体以及多目录/多 Repo 管理；
- Worktree 创建、切换、清理和 Session 归属；
- 持久交互终端；
- 完整 Git 状态、文件级/块级 Review、Stage/Commit/Ship；
- Checkpoint 与 Git/文件恢复的一致关系。

这是 Amiba 和官方 Desktop 之间最明显的日常生产力差距之一，也直接关系到个人托管 Extension 的安全修改流程，应列为 P0。

### 4.6 Profile、人格、Memory、Curator 与 Starmap

Amiba 已覆盖：

- Profile 创建、重命名、删除、切换；
- Profile Description、SOUL、模型、Skills、Tools 和 Memory 查看；
- 独立人格管理；
- Hermes Memory 文件的只读浏览。

官方额外提供：

- Memory Provider 的安装、切换、重置和状态管理；
- Curator 的暂停、立即运行和学习维护；
- Starmap / Journey 的记忆关系图、时间线和分享；
- 运行中 Agent / Subagent 的实时树状观察。

建议把它们分成两个产品入口：

- “记忆与学习”：Memory Provider、Curator、Starmap；
- “运行中的 Agents”：树状状态、当前 Tool、文件活动、Token、停止/进入 Session。

当前名为“Agents”的设置页实际管理的是 Hermes Profiles，容易与官方的“运行中 Agents”混淆，建议产品文案改为“Profiles / 助手配置”。

### 4.7 Cron、Kanban 与自动化

Cron 已基本完整覆盖：

- 创建、编辑、删除；
- 暂停、恢复、立即运行；
- 模型、Provider、Skills、脚本、工作目录和投递目标；
- 运行记录和状态筛选。

Kanban / Task Center 目前只覆盖：

- Board 和任务浏览；
- 搜索和按状态分组；
- 创建任务并指定 Profile、工作目录等信息。

缺少任务编辑、移动状态、重新分配、删除、子任务和附件等完整生命周期。官方能力仍可由内置 Hermes 命令使用，但 Amiba UI 尚未覆盖。

### 4.8 Messaging、Webhook 与 Pairing

Hermes 0.20 将 Telegram、WhatsApp、Slack、Discord 等消息平台视为正式入口，并提供：

- 平台配置与连接状态；
- 登录/配对和测试；
- 消息平台 Session 分组；
- Webhook CRUD 与启停；
- Pairing 请求批准、撤销和清理；
- Cron 结果投递。

Amiba 可以识别并展示部分消息来源，Cron 也能保存投递目标，但缺少完整的消息平台设置、Webhook 和 Pairing 管理面。该模块应视为未覆盖，而不是“Runtime 里已有所以已完成”。

### 4.9 Artifacts 与统一 Extension Center

Hermes Desktop 0.20 中实际存在两种名为 Artifact 的体验：

1. **跨会话产物页**：扫描最近 Session 的消息和 Tool 结果，汇总图片、文件和链接，支持筛选、搜索并返回来源会话。
2. **会话内生成内容预览**：识别较完整的 HTML、SVG 和长代码，按 Session 与标题归并版本，在右侧 Pane 中预览。Registry 本身在内存中，真正持久化的仍是消息 Transcript。

它们都不是 CLI Runtime 或 Web 后端，也不是一种可安装应用格式。HTML 预览只是在受限 iframe 中运行浏览器 JavaScript。

因此 Amiba 不需要复制一个独立 Artifact 一级对象。已经冻结的统一方案是正确的，而且能力上可以做成官方的超集：

| 官方需求 | Amiba 统一方案 |
|---|---|
| 会话内即时预览 | 保持为 Message Preview，不自动安装 |
| 跨 Session 搜索图片、文件、链接和内容 | Extension Center 统一搜索 Extension 与 Output |
| 从产物回到来源聊天 | Output 保存 `sourceSessionId`、来源 Tool 和 Revision |
| 多次生成的版本 | 未保存时跟随 Transcript；保存后由 Git + Revision 管理 |
| 长期收藏与分类 | 保存为 `static-content` / `interactive-ui` Extension，支持标签、合集、收藏 |
| 进一步变成工具 | 保持 Extension ID，升级为 `tool-app` 并增加 MCP Tools |
| 命令行或 Web 后端 | Node/Python MCP Server Runtime，而不是浏览器 Preview |

为达到官方覆盖，Extension Center 的第一版至少要包括：

1. 最近 Session 中图片、文件、链接、HTML/SVG/长代码的可搜索索引；
2. 不保存也能在会话中预览；
3. 显式“保存为我的创作 / 工具”；
4. Extension 的统一搜索、标签、合集、来源 Session 和删除恢复；
5. Extension Output 的收藏、预览和来源追踪；
6. 最新主内容默认展示，源码变化由 Git 保留，部署状态由 Revision 保留；
7. 静态内容、交互 UI、CLI/后端 Tool 共用同一个 Extension 生命周期。

### 4.10 配置、运维、安全与恢复

Hermes Web Dashboard 和 CLI 还承担一套完整控制面：

- Schema 化配置、Raw YAML、默认值、导入导出和迁移；
- 环境变量的脱敏查看、写入、删除和按需 Reveal；
- Gateway 启停、重启、更新检查；
- Doctor、Security Audit、Egress、Secrets；
- Backup、Import、Debug Share、Prompt Size 和 Dump；
- Hooks 管理；
- Checkpoint 列表和清理；
- 系统资源、日志、使用量和 Curator 状态。

Amiba 已有托管 Runtime、状态、日志和更新能力，但其余大部分没有正式 UI。建议建立一个“系统与诊断”页统一承接，不需要照搬官方 Dashboard 的每一个菜单。

### 4.11 远程 Gateway 与 Hermes Cloud

Hermes Desktop 0.20 支持本地托管、远程 Gateway 和 Hermes Cloud，并处理远程认证、文件和媒体访问差异。

Amiba 当前以本地托管 Runtime 和本地 Backplane 为主。Terminal Tool 可以选择 SSH Backend，但这不等于 Desktop 连接远程 Hermes Gateway。

如果 Amiba 目标包含多设备、服务器 Agent 或企业部署，需要补：

- Gateway URL 和连接模式；
- Token/OAuth 登录、过期和重新认证；
- 远程文件、附件、媒体和预览代理；
- 连接切换时的 Session/Profile 能力探测；
- 本地能力不可用于远端时的清晰降级提示。

### 4.12 CLI / TUI 覆盖策略

Hermes 0.20 CLI 包含对话、模型、Gateway、Cron、Skills、Tools、MCP、Session、Profile、Plugin、Memory、Backup、Doctor、Security、Webhook、Kanban、Curator、Journey、Checkpoint 等大量命令，TUI 还提供 Session 切换、分支、回滚、后台任务、语音和 Agent 树。

Amiba CLI 当前职责是 Extension 开发：

- `amiba create`
- `amiba create-mention-source`
- `amiba dev`
- `amiba build`
- `amiba pack`
- `amiba install`

不建议在 TypeScript 中重新实现一套 Hermes CLI，也不需要让用户输入 `hermes -- <args>`。更稳妥的方式是让 Amiba CLI 在内部读取 Hermes Command Registry，并把官方命令直接映射为 Amiba 命令：

```text
amiba chat
amiba status
amiba sessions ...
amiba mcp ...
amiba doctor
amiba logs
amiba dashboard

amiba extension create      # Amiba Extension 开发命令归入 extension 命名空间
amiba extension dev
amiba extension build
amiba extension pack
amiba extension install
```

实现上由 Amiba Dispatcher 启动托管 Runtime 中的 Hermes 命令入口，并传入原始参数；Help、补全和子命令元数据从 Command Registry 生成，避免手写第二份命令表。Dispatcher 必须使用与 Desktop 相同的 Hermes Home、Profile、Runtime 和版本，不能悄悄调用系统里另一份 Hermes。

现有 `amiba create/dev/build/pack/install` 不保留兼容别名，直接统一为 `amiba extension create/dev/build/pack/install`。独立的 `create-mention-source` 也不进入新 CLI；Mention Contribution 按统一 Extension 方案随 Extension 创建和发布。这样最新版本只有一套清晰命令结构，用户看到的是 Amiba CLI，内部仍复用官方 Hermes 实现。

### 4.13 Web / 浏览器覆盖策略

官方 Web 是管理 Dashboard；Amiba 浏览器扩展是网页内 Agent Surface。两者定位不同：

- Amiba 已有侧栏、新标签页、全屏 Chat、网页上下文、`@page`、浏览器执行桥接和 Userscript Runtime；
- 但它不等价于官方的 Session、Files、Analytics、MCP、Channels、Webhooks、Config、Env 和 System 管理页。

不必把全部管理页塞进浏览器扩展。建议：

- 日常网页任务继续由浏览器扩展负责；
- 完整管理能力优先放在 Desktop；
- 如果未来支持远程部署，再提供轻量 Web Control Center，共用同一套 API 和能力探测。

## 6. 建议的实施顺序

### 阶段 A：先建立“不会再次漏能力”的底座

- 建立 `HermesCapability` 清单和自动化快照；
- 每项能力记录 `native`、`internal-mapped`、`designed`、`unsupported`；
- 增加 Amiba CLI 内部命令 Dispatcher；
- 修正过期的 API parity 文档。

验收标准：升级 Hermes 后，CI 能明确告诉我们新增了哪些命令、路由、事件和配置能力，而不是靠人工重新扫代码。

### 阶段 B：补齐日常生产力主链路

- Project / Repo / Worktree；
- Terminal Pane 与 Git Review；
- Session FTS、Branch/Fork、Checkpoint/Rollback；
- Agent/Subagent 观察。

验收标准：用户在 Amiba Desktop 中能够完成官方 Desktop 的主要 Coding Agent 工作流，不需要切回 Hermes TUI。

### 阶段 C：落地统一 Extension Center

- 先覆盖官方 Artifact 浏览和预览；
- 再实现显式保存、Git、Revision、Output；
- 最后补齐 Node/Python Runtime、Registered MCP、权限和发布。

验收标准：报告、网页、图片合集、交互页面和后端工具都能进入同一个长期管理体系，并且没有第二套 Artifact 生命周期。

### 阶段 D：补齐控制面

- Skills/Plugins/MCP Hub；
- Provider OAuth/Credential Pool；
- Messaging/Webhooks/Pairing；
- 系统诊断、备份、安全和远程 Gateway。

验收标准：官方 Web Dashboard 的关键管理任务都能在 Amiba Desktop 或 CLI 中完成。

## 7. 架构约束

1. **覆盖产品能力，不机械复制页面。** 官方 Web 的功能可以由 Amiba Desktop 承接。
2. **Runtime 中存在不等于已覆盖。** 必须有可发现入口、错误反馈和恢复路径。
3. **优先复用 Hermes 真源。** CLI Command Registry、配置 Schema、MCP Catalog 和 Skills Hub 不应在 Amiba 手写第二份静态清单。
4. **所有适配必须做能力探测。** Amiba 固定的 0.20 Snapshot 比 Release tag 新，未来也会继续变化，不能只比较版本字符串。
5. **Extension 是唯一长期内容与能力对象。** Artifact 只用于描述官方现状或临时 Preview，不进入 Amiba 领域模型。
6. **Agent 代操作不能替代确定性管理。** 安装、授权、删除、回滚和迁移必须有直接 UI/API 与审计。
7. **安全能力必须实际执行。** Manifest 中声明但 Host 不拦截的权限，不算实现。

---

## 8. 验收门槛

当以下条件同时满足时，才可以对外宣称“Amiba 覆盖 Hermes 0.20 官方能力”：

- 官方 CLI 的全部非废弃命令可通过 Amiba 原生入口或托管 CLI 透传使用；
- 官方 Desktop 的核心 Chat、Session、Project、Worktree、Terminal、Review、Artifacts 和 Agents 工作流有等价入口；
- 官方 Web 的 Session、Files、Models、Cron、Skills、Plugins、MCP、Profiles、Channels、Webhooks、Pairing、Config、Env 和 System 管理任务有等价入口或明确的不适用说明；
- 每个缺失项都有显式决策，而不是因为没有发现；
- Hermes 升级时，自动化能力快照能够阻止无意的能力倒退；
- Extension Center 已覆盖官方 Artifact 的找回、搜索、预览、来源追踪和长期保存，并额外支持交互 UI 与后端 Runtime。
